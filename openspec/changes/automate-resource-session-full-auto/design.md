## Goals / Non-Goals

**Goals:** a server-owned, resumable journey from one informed authorization through generation; no routine preview, take entry or intermediate clicks for eligible inputs; exact source identity; deterministic wardrobe/coverage semantics; bounded and recoverable failures.

**Non-Goals:** arbitrary prose-to-anatomy inference, automatic translation approval, automatic fused-scene decomposition, vision-based pixel certification, automatic image rerolling, a distributed job platform, or repairing existing generated sessions. Manual and expert flows remain available. No production code or real generation is part of this planning delivery.

## Decisions

### 1. Opt-in creation and precise authorization

Extend `POST /api/sessions/guided` with optional `saved_look` and `full_auto` objects. Omitted additions stay omitted from the canonical request digest, preserving old replays. `saved_look` is exactly `{look_key, version, content_digest}`. `full_auto` is exactly `{authorization_version: 1, generate_without_pauses: true, profile_revision, profile_digest, progression: "all_stages_full_interval", framing_intent: "vary"|"full_body", scope_digest, scope_issued_at}`. Unknown fields and coercions fail before writes. Full Auto requires automatic mode and saved_look. Raw look/wardrobe overrides must be absent or empty when saved_look is supplied; competing values fail before writes and point to the existing manual post-creation Keep/Replace flow.

Resolve profile/room/workflow eligibility without remote calls. V1 requires explicitly classified t2i with compatible mapping/model and no required reference; empty kind, edit, guide, angles and scene return full_auto_workflow_unsupported and offer manual flow. Current composition strips context only on its reference branch and according to graph kind, not merely because a primary workflow is labeled edit. Do not extend guided creation with an unplanned reference acquisition pipeline. In one existing guided transaction, load the exact saved version, verify both digests, create the initial plan with look snapshot, resolved permanent appearance, fully worn wardrobe, progression events and take coverage, and persist the authorization/run record with the guided response. Pure candidate-building logic is shared with existing look/progression services; no intermediate externally visible empty-look session is permitted. Creation returns 201 (200 on replay), retaining the normal response fields and adding `full_auto_run_id` only for this opt-in. Dispatch only after commit; startup discovers persisted undispatched runs. A failed transaction leaves no session, run, approval or request receipt.

The UI obtains the read-only consent preflight described in Decision 14 and displays the version, profile readiness, initial/final stage, stage count, photo count, effective workflow/provider, framing/canvas, allowances/deadline and the meaning of Generate without pauses before the single action. It explicitly states that unchanged authorized work continues after browser closure and resumes after backend restart. The optional saved-look selector is also available at manual creation, applying only the exact snapshot without progression or a Full Auto run. The button authorizes bounded automatic creative choices, stage/coverage application, policy-based review approval, submission and one initial execution attempt per take. It does not authorize silently changing the look, accepting arbitrary adaptations, retrying failed images indefinitely or claiming human prompt review.

Character/model selection is hidden only when existing navigation supplies an unambiguous valid selection. The backend still requires a valid model record, including for workflows without a character LoRA; it does not allocate a synthetic identity. Checkpoint/LoRA mapping remains conditional on graph kind and explicit choices. Workflow override remains Advanced; no global default is guessed.

Alternative rejected: creating the session and then applying whichever look is latest permits drift and partially initialized sessions. Alternative rejected: simulating UI clicks is neither durable nor authoritative.

### 2. Small versioned automation profile, no authoring-v1 schema rewrite

Keep the exact authoring-v1 and portable look-v1 formats. Add an immutable `saved_look_automation_profile` record keyed by look key/version, profile revision and canonical digest, bound to the look content digest. This is the existing canonical SHA-256 digest of `{appearance, outfit}` from saved-look snapshot validation, not portable_content_digest or the export-envelope hash. Publish a new profile revision on edits; no mutation of historical evidence. Profile readiness is additive to normal look usability. Portable-v1 import/export continues to exclude the profile, with an explicit notice that automation readiness does not transfer; do not silently widen the portable format.

Profile v1 is a closed object with `schema_version`, exact look binding, `appearance_segments`, `garment_coverage`, `baseline_coverage`, `inventory_complete`, and authored provenance. Each appearance segment has stable ID, exact source span/text and owner `permanent` or `garment:<key>`. Spans must partition appearance without overlap, omission or fabricated wording. Only permanent segments compose constant appearance; garment segments are represented solely by the canonical outfit wording, after a user confirms equivalence. If the text cannot be partitioned cleanly, create a corrected look version in Looks. No model silently edits fixed appearance. A corrected profile can resolve an overlap without changing the underlying immutable source, but its resolution is separately visible and digest-bound. Before any shot is linked, an explicit session profile-application operation accepts exact profile revision/digest and expected plan revision, fences the run, rebuilds only the derived projection/coverage through CAS and invalidates affected preparations. After any shot is linked, the session profile is frozen with the look snapshot; a different profile requires a new session.

Garment coverage entries reference exact garment keys. For each worn/aside state, they declare coverage of chest, hips, legs and feet as full, partial, none or unknown; removable accessories can explicitly declare no body coverage. Baseline coverage declares those same regions for the state with every listed outfit item absent, not the initial fully worn outfit. Explicit none is an accepted uncovered-region assertion; missing data is unknown, never none. An appearance-only look has one constant stage, no events and empty wardrobe text; it can be eligible with explicitly accepted baseline/inventory facts shown as compiled coverage in the consent summary, without adding a no-clothing wardrobe sentence. These are prompt-detail regions, not anatomy recognition. Unknown is valid storage but not sufficient Full Auto coverage. `inventory_complete` must be explicitly confirmed for automatic uncovered-region claims; no garment-list omission means bare. Aside coverage is mandatory only when that stage exists. Each accepted assertion records origin (user or reviewed structured source), source identity/digest and acceptance revision. Unreviewed photo/assistant suggestions cannot supply authoritative facts.

This is one reusable look-level setup, not per-take work. Existing structured, previously reviewed evidence may populate entries automatically when it expresses the exact same regions/states. Current free-text look/garment rows alone do not do so. A future assistant can propose profile edits for user review in Looks; implementing a new extractor is not required here.

Alternative rejected: guessing coverage from words such as skirt, boots or bracelet fails for layers, partial garments and moved-aside states. Alternative rejected: extending every existing closed snapshot/import schema introduces unnecessary compatibility work.

### 3. Deterministic progression and coverage compilation

The user explicitly selected all saved stages across all takes. For N takes and K derived stages, reuse `floor(i * (K - 1) / (N - 1))`, with K=1 constant and N>=K for K>1. Include every authored removal stage and the existing final-garment aside stage if present. Initial and final stages occur at first and last take. N<K is a preflight error with required count; never skip stages or invent order. Count remains 1..500 and is used for schedule materialization only, not writer creative context/digest. An appearance-only look has no outfit progression and requires explicit baseline coverage if used for Full Auto; absence of an outfit is not a garment-free instruction.

Materialize minimal from_here events once using stable take IDs. Do not redistribute after reorder/add/remove; edits pause/fence the run and use existing invalidation. A new plan cannot have event collisions; resuming never reapplies the progression. Continuing an edited manual plan requires the user to resolve existing events explicitly.

Compile each stage from its explicit garment states and baseline. Per region, full coverage wins over partial; partial wins over none; uncovered wording requires complete inventory, known baseline and no remaining full/partial cover. Unknown applicable evidence blocks Full Auto rather than manufacturing a bare assertion. Preserve separate garment/accessory presence; removing a bracelet says nothing about wrist or hand coverage. Use deterministic English templates, record exact compiler version and profile/stage digest, and validate the existing text length/control-character rules. A garment-free final stage requires a baseline with no additional worn covering items; contradictory baseline facts block eligibility. The four-field creative writer still cannot generate or overwrite coverage.

Store immutable session profile evidence and per-take coverage provenance outside the closed authoring block, keyed by session/revision/stable take ID and text digest. Apply all initial coverage in the creation transaction. Include consumed profile, ownership and coverage digests in preparation/finalization evidence and copy-forward comparisons. Keep the resource/adaptation-only digest's meaning unchanged. Manual text edits revoke derived provenance for affected takes and pause Full Auto; they do not relabel server text as user-authored. Generated snapshots stay frozen.

### 4. Resolve competing appearance at its owner

The snapshot remains complete historical source; `plan.look` uses the accepted permanent projection. When identical to snapshot appearance, retain origin saved_look. When a reviewed ownership projection differs, use the existing user origin plus the separate profile acceptance evidence, never forge saved_look equality or assistant provenance. Enforce that relationship server-side during Full Auto preparation and explicit manual profile application. Profile-free manual sessions retain snapshot semantics, including the known possibility of contradictory unreviewed prose; this change does not rewrite historical sessions. Explicit manual profile application reuses the same CAS/provenance/freeze rules while preserving manual progression preview, review, submission and Run. Profile existence alone never silently changes a manual session.

For the invented bracelet regression, ownership labels the bracelet clause as the same progressive accessory key. The constant projection excludes it; worn-stage wardrobe includes its canonical wording; removed-stage wardrobe and all positive prompt sections do not reintroduce it. This is an explicit reusable ownership decision, not automatic substring deletion. If a clause is marked permanent but the same accessory is removed, block `appearance_progression_conflict`. Keep means retaining it and changing progression; removing means correcting ownership/profile or the saved look. Full Auto does not silently choose either.

Inspect all consumed text sources, including model base prompt, authorized room prose, writer choices and adaptations. Existing structural conflicts/unresolved placeholders/stale adaptations remain blocking. The current `detect_take_conflicts` inspects fused-scene structural conflicts, not arbitrary room/appearance semantics; the profile ownership check is new and must be tested independently. No existing helper is treated as a universal semantic validator. Deterministic structured ownership contradictions are blockers. Semantic checks may return evidenced conflicts or uncertain findings for correction, but cannot claim exhaustive proof or silently adapt prose. Neutral `resource_descriptive_vs_plan_constants` markers remain visible notices; they alone are not semantic conflicts. The single authorization permits policy review of those notices and valid generated choices; actual conflict/adaptation approvals still require explicit resolution. This limited automatic-review exception must update the current review-only contracts, not merely alter UI gating.

### 5. Persist orchestration, reuse stage services

Add one small `resource_full_auto` coordinator with additive SQLite run/checkpoint persistence. Run states are `active`, `waiting_authoring`, `waiting_runner`, `blocked`, `cancel_requested`, `cancelled`, `failed`, `succeeded`, and `completed_with_errors`; phase is separate (`prepare`, `validate`, `approve`, `submit`, `execute`, `reconcile`). Persist authorization digest/version, expected plan revision, frozen input digest, target IDs, child operation IDs, completed work, action receipts, blocker and timestamps. A monotonic run revision supports control CAS. At most one live Full Auto owner exists per session, with the same lease/fencing discipline as authoring operations.

Only the owning coordinator can start child authoring operations while a run owns the session. Pass an internal authenticated ownership capability, never a browser owner token. Manual prepare/suggest/run/submit/retry and another Full Auto request must not race that owner. Ownership checks belong in shared mutation/service boundaries as well as routes. A deliberate edit first pauses/fences ownership, then applies existing plan CAS. A manual-transfer request uses the existing Cancel path and stays pending while any owned attempt is pending or unknown; Full Auto retains its owner/fence and manual mutations remain blocked until all owned attempts are verified settled. After settlement, the pending transfer SHALL release ownership without resuming or dispatching Full Auto. Same-request replays remain allowed. Reuse the existing bounded authoring worker rather than add a second assistant loop.

Phases:

1. Prepare ordered remaining takes in child operations of at most 20; chain batches server-side. Incrementally persist existing snapshots; do not regenerate valid completed or linked ones.
2. Validate all targets are current and ready/linked, all required provenance/dependencies are valid, and no unresolved conflicts, placeholder, duplicate-review flags or stale adaptations remain. No submission begins while later takes are still unvalidated.
3. Invoke existing approval service for the exact revision, storing separate automatic authorization provenance and the validated target/snapshot digest. The record says policy-approved, not human-reviewed. Add a shared atomic gate so a direct client cannot bypass Full Auto blockers using existing approval/submission routes.
4. Invoke existing submission service for each target in order. Persist receipts with links; replay already linked snapshots. A partial submission is recoverable without new shots. Revalidate authorization/current dependencies on each write.
5. Start the existing runner after all targets are linked and the global GPU is available. Preserve serial order, prompt snapshots, seed rules, unique output prefixes, reference graph-kind behavior and locked-file retry.

All phase transitions check current run fence, authorization, revision and cancellation transactionally. No database transaction spans an assistant or ComfyUI request. Persist durable intentions before side effects and reconcile their receipts before advancing after a crash.

Discovery: GET `/api/sessions/{sid}/full-auto` returns HTTP 200 with `{current_run: <public view or null>}` for an existing session (404 if missing), selecting the nonterminal run or most recent terminal run by creation sequence. Controls: GET `/api/sessions/{sid}/full-auto/{run_id}`; POST to its `/cancel` and `/resume` with request_id, expected_run_revision and expected_plan_revision. Resume also accepts an explicit changed-scope authorization digest when corrections changed the frozen inputs; an old authorization cannot silently cover them. Cancel returns 202 while work settles and 200 once terminal; resumed work returns 202, identical replay 200, stale/conflicting controls 409. Status gives phase, distinct prepared/submitted/completed/failed/cancelled counts, affected take/shot IDs, safe blocker code/message, available remedies and can_cancel/can_resume; never raw private payloads, leases' owner secrets or paths.

### 6. Cancellation, restart and ambiguous remote execution

The authorization survives browser closure and service restart for unchanged inputs. Startup expires prior leases, reconciles persisted work and resumes eligible non-cancelled runs automatically. Failures requiring user action remain blocked; cancelled runs never restart themselves. A blocked run with pending cancel intent is ineligible for automatic reconciliation or ordinary Resume. Explicit Resume of a blocked run without pending cancel intent reuses the scope after correction, and records a replacement authorization when accepted edits change its digest. Look/workflow/character changes after generated state require a new session; ordinary existing safe edits retain normal continuity rules.

Cancellation persists first, fences authoring and stops scheduling. Late assistant output is discarded. Pending submitted shots retain IDs and become cancelled; an active GPU attempt is interrupted only with verified atomic targeted cancellation; otherwise it drains as described in Decision 11. An already completed image is kept and reported as a cancellation race. No unrelated ComfyUI job is interrupted. Repeated Cancel is idempotent. Resume never creates new shot rows for linked takes; with pending cancel intent, the existing Resume control is reconciliation-only as described in Decision 11.

Add an execution-attempt journal to the existing runner: stable attempt ID, shot ID, seed, unique filename prefix, graph digest, dispatch state and nullable ComfyUI prompt ID. Persist dispatch intent before `/prompt`; record acknowledgement before polling. Use the explicit client-UUID or legacy-correlation contract in Decision 11; neither permits blind retransmission after uncertain acceptance. A known prompt ID is polled/recovered, not requeued; a completed output is adopted once through normal file handling.

If dispatch may have happened but cannot be reconciled, block `execution_outcome_unknown`. Missing queue/history alone is not proof of non-execution. Do not auto-reset that shot via the existing retry endpoint. The user may explicitly authorize a new attempt after an explanation of possible extra remote work; reuse the shot ID and retain prior attempt evidence. Guarantee unique session/take/shot allocation and no blind ambiguous resend, not exactly-once remote execution or billing. Definitively failed/cancelled attempts can be explicitly retried on the same shot; successful shots remain untouched. Initial Full Auto has no automatic image-reroll loop.

Use a durable global runner claim shared by manual and Full Auto entry points in addition to the in-process task, with lease recovery/fencing. A busy GPU puts the run in waiting_runner without stealing it. Before dispatch, recheck frozen workflow/settings/character inputs; live model base-prompt, LoRA, settings or workflow drift cannot silently change what was authorized. Modify startup's blanket running-to-failed treatment only for journaled attempts requiring reconciliation; preserve legacy recovery behavior where no journal exists.

### 7. Real blockers and recoveries

| Condition | Behavior / remedy |
| --- | --- |
| Look/profile missing, stale digest, incomplete inventory/coverage, unowned appearance | Preflight refuses allocation; open Looks to correct once and choose the exact resulting version/profile. |
| Fewer takes than stages | Refuse with required count; increase count or use manual custom progression. |
| Missing character/workflow/mapping, invalid canvas, not-ready room | Refuse creation with the relevant selector/setup/readiness action. No automatic translation acceptance. |
| Neutral room notices only | Show notices; continue under recorded Full Auto policy authorization. |
| Real structural/ownership conflict, stale adaptation, duplicate tuple, invalid writer result | Block with take IDs, source fields and correction/review action. Do not delete takes, silently approve or loop forever. |
| Assistant unavailable/transport failure | Preserve completed batch work; show configuration/retry and resume remaining work. |
| Resource/translation drift or external plan edit | Fence and block; explicit refresh/correction, CAS and renewed scope before only affected work is prepared again. |
| Changed bound workflow or frozen look after generation | Explain new-session requirement, keep existing results. |
| GPU busy | Wait with progress; retain cancel capability and start only when ownership can be claimed. |
| Known per-shot execution failure | Continue remaining shots; final completed_with_errors exposes failed-shot retry. All failed means failed. |
| Ambiguous remote dispatch | Block and reconcile; no unattended resend. |
| Feature flag disabled | No new Full Auto creation, authoring, approval, automatic submit/start/resume. Reads/cancel remain; already running work may settle. Existing explicitly approved manual submission policy is unchanged. |

### 8. Canvas and framing are separate from coverage

Preserve paired positive integer multiples-of-eight width/height validation, inherited dimensions when omitted and custom UI defaults 768 by 1360 only when enabled. Show effective dimensions before consent. Validate usable unconnected mapped slots for explicit dimensions; never overwrite connected inputs. No dimension change is claimed to guarantee visible feet.

Default framing_intent is vary. Choosing full_body sets variation_policy.framing to fixed with user origin and the exact value `Full body, head to toe, both feet visible, with space above the head and below the feet.` Camera/pose remain variable subject to that constraint. An already fixed different framing value fails preflight with framing_conflict; this does not require guessing whether arbitrary prose means close-up. Existing structured fixed-value checks reject conflicting writer framing. Free-text contradictions outside those checks are not exhaustively detected. Coverage describes clothing state, not what must be visible. Neither mode guarantees anatomical accuracy, cloth fidelity or subject fit. Results show instructions and actual images separately; no visual-success badge is inferred from prompt text or successful generation. Visual correction/reroll remains an explicit later action.

### 9. Operating policy, transitions and ownership lifetime

Reuse `resource_planning.is_enabled()`: config `resource_planning_enabled` defaults to true and `IDEVGEN_RESOURCE_PLANNING_ENABLED` takes precedence. No second feature flag is needed. Enabled only exposes the opt-in capability, never authorizes a run. Check the live flag before each new Full Auto dispatch; disablement permits settlement of dispatched work, then blocks `resource_planning_disabled`. Re-enabling permits explicit Resume of blocked runs without pending cancel intent; runs with pending intent permit cancellation reconciliation only.

`authorization_version: 1` versions the wire/evidence shape. Server-owned `policy_version: "resource-full-auto-v1"` identifies the eligibility, approval, template, scheduling, retry and expiry rules in this design. Persist both; never reinterpret an old authorization under new rules. A behavior change increments policy_version; an unsupported recorded policy blocks `policy_changed` pending displayed renewed consent.

Terminal means an execution epoch has stopped. Initial creation starts epoch 1. Explicit Resume of cancelled, failed or completed_with_errors can open a new fenced epoch on the same run ID, preserving targets, counters and receipts. It creates no duplicate run or shot. Succeeded is non-resumable. Old control replay returns its stored result without reactivating an old epoch. Nonterminal states are active, waiting_authoring, waiting_runner, blocked and cancel_requested. Blocked reserves the run identity but holds no worker lease; pending cancel intent bars ordinary continuation and dispatch.

| From | Event | To / effect |
| --- | --- | --- |
| New durable creation | Worker admitted | active, epoch 1 |
| active | Assistant slot or runner unavailable | waiting_authoring or waiting_runner |
| Either waiting state | FIFO admission and valid authorization | active |
| active or either waiting state | Correctable input/dependency/refusal/drift/budget/expiry failure | blocked, with reason and released idle claims |
| active or either waiting state | Unexpected internal failure | failed after owned work settles; unknown remote work blocks reconciliation instead |
| active, either waiting state or blocked without cancel intent | Cancel | cancel_requested while owned work settles, otherwise cancelled |
| cancel_requested | Bounded ComfyUI probes exhaust or outcome remains unknown | blocked with cancel intent and attempt/shot evidence retained; no worker lease or scheduling |
| cancel_requested | Last owned result/attempt is verified settled | cancelled, preserving successful outputs and scheduling no new work |
| blocked with cancel intent | Cancel replay | unchanged; no poll or dispatch |
| blocked with cancel intent | Explicit Resume, labeled `Reconcile cancellation` | reacquire a fenced lease for read-only reconciliation; stay blocked on outage/unknown, enter cancel_requested for a verified running attempt, or cancelled after verified settlement |
| blocked without cancel intent | Explicit valid correction/Resume | active or required waiting state, new fence |
| cancelled, failed or completed_with_errors | Explicit eligible Resume | active or required waiting state, epoch increment |
| active execute | All targets successful | succeeded |
| active execute | Settled mix of successful and failed targets | completed_with_errors |
| active execute | All targets failed | failed |
| Any nonterminal | Restart or lease loss | Recover same state/phase; do not reverse cancellation or unblock automatically |

Other transitions fail without mutation. Preparation/provider failures are actionable blocked states; failed means an unexpected internal failure or all shots failing. Persisted cancellation wins at the next serialized transition while retaining already produced images. No terminal outcome is recorded while an owned remote attempt remains unresolved unless its unknown outcome is explicitly risk-accepted under Decision 11; retain that evidence and deletion/rollback guards while remote work may still be active.

Coordinator and global runner claims have 60-second leases and asynchronous 15-second heartbeats, including during remote I/O. Renewal checks fence and epoch. Waiting runs own no runner claim; their coordinator lease is renewed or released for the next scheduler tick. Blocked/terminal runs hold no idle worker lease. Child authoring operations retain their independent ten-minute lease contract. Coordinator expiry does not steal a live child lease: recover its status, wait for the owner or expiry, then resume remaining work. Runner expiry never proves GPU work stopped; reconcile its prior dispatch before another app dispatch. Clock/scheduler stalls fail closed.

Allow one in-flight Full Auto assistant HTTP request across sessions, including compatibility fallback. Reuse ownership primitives for an assistant slot with a ten-minute lease and 15-second heartbeat; after owner loss quarantine it through the in-flight request timeout. Admit takes FIFO by persisted ready timestamp and run ID, yielding after each take. This does not throttle unrelated manual assistant calls or external applications. Runner admission is FIFO by runner-ready timestamp and run ID, skipping blocked/cancelled/expired runs. Manual Run remains immediate: shared transactional admission returns 409 runner_busy when an owner or eligible prior Full Auto waiter exists, and never queues manual work or preempts a session. With no eligible waiter it can claim the idle runner normally. An admitted session retains serial execution until it settles or blocks; no general queue framework is needed.

Before each GPU dispatch observe the remote queue. External work keeps the run in waiting_runner with an external-busy reason, without holding an idle runner claim. Send only one owned attempt at a time at normal priority. An external client can race that observation: app claims do not promise exclusive remote-server ownership or fairness against external clients. Time queued behind external work is not executing-shot time; the existing 900-second timeout begins when the owned prompt is observed executing. A missed running observation followed by history completion is a normal recovered completion.

### 10. Bounded calls, unavailable dependencies and renewed consent

Policy v1 permits at most two assistant HTTP dispatches per take and `2 * target_count` per authorization, including the existing reasoning-parameter fallback. Reserve counters durably before each physical request, including inside _request_completion before its compatibility fallback; recheck ownership, cancellation, expiry and provider identity there. Expose structured safe transport status/Retry-After/refusal metadata instead of parsing the current flattened error string, preserving existing unrelated manual behavior. A lost response still consumes a reservation. A provider needing fallback every time consumes both calls on a successful take; a later recovery can therefore require extra consent, which the UI must state. Add no automatic retry for invalid output, refusal or transport failure. Explicit recovery exceeding the per-take/overall allowance requires a displayed additional budget authorization, preserving cumulative counters. Provider usage is recorded when available; call limits are not a monetary-cap guarantee.

Initial authorization expires seven days after the server-issued preflight timestamp, persisted in UTC and displayed before consent; creation does not extend that deadline. Expiry stops new calls/images, settles or reconciles already dispatched work and blocks `authorization_expired`. Waiting runs use the same deadline. Blocked history remains without workers or polling until explicit renewal/cancellation; expiry does not delete evidence or justify a global interrupt. Existing assistant 300-second request and runner 900-second executing-shot timeouts remain; the optional compatibility fallback consumes a second bounded request.

Startup recovers local records first. Missing assistant configuration blocks `assistant_unavailable` before dispatch. Transport/rate-limit failures block `assistant_transport_error` or `assistant_rate_limited`; explicit Resume respects Retry-After when supplied. A structured provider refusal/content-filter signal blocks `assistant_refused`, offering brief/stage revision or manual authoring. Unclassified free text stays `writer_output_invalid`. Never rewrite to evade provider policy, silently remove stages or repeatedly retry a refusal.

Unavailable ComfyUI during reconciliation or before dispatch receives at most three read-only retry probes after delays of 5, 15 and 30 seconds, with the retry count persisted across restarts, then blocks `comfy_unavailable`. These probes never resend `/prompt`. Busy queues are polled at most once per 15 seconds until admission, cancellation or expiry. An unresolvable dispatch stays `execution_outcome_unknown` even after connectivity returns.

For blocked runs without pending cancel intent, a SessionView Resume panel for changed inputs/budgets compares old/new look/profile, room/resource/adaptation digests, ordered remaining targets, stage/coverage assignments, brief/creative policy, model/workflow/settings, provider identity/model, policy/compiler versions, remaining call/attempt allowances and deadline. The backend issues a scope digest bound to current run/plan revisions. Resume submits it with `accept_changed_scope: true`, request_id and expected revisions; the server recomputes it atomically and stores new authorization linked to the old one. Unchanged Resume needs no second consent panel. Bind a non-secret endpoint identity digest internally, never display credentials or raw private provider URLs. Generated-continuity restrictions still require a new session when applicable.

### 11. ComfyUI capabilities and cancellation fallback

The inspected official [server](https://github.com/Comfy-Org/ComfyUI/blob/master/server.py) accepts client UUIDs in `/prompt` and exposes `/api/jobs/{job_id}/cancel`. The inspected [queue](https://github.com/Comfy-Org/ComfyUI/blob/master/execution.py) provides atomic `interrupt_if_running`, while `put` does not deduplicate IDs. These upstream observations do not verify the user's installed server.

The conservative correlation/draining path is the supported default, not a temporary failure mode. Task 5.3 owns capability evidence fixtures and any verified version mapping; no entries may be guessed from version numbers or upstream master. An empty verified set is acceptable only if the conservative journey and recovery acceptance pass and UI discloses draining. Do not require a guessed minimum version. Resolve capabilities from advertised metadata or a mapping of tested versions, defaulting unknown capabilities to the conservative path. Never probe support by generating an image or issuing a destructive interrupt. Freeze capability evidence per attempt and invalidate it on server identity/version change.

With verified client-ID support, persist a canonical attempt UUID before dispatch, send it once as prompt_id, require a matching acknowledgement and reconcile queue/history by that ID. ### 12. Deletion and downgrade boundaries

Current model deletion can cascade sessions, workflow deletion can null bindings, and session deletion checks only the current runner. Add transactional Full Auto guards: deleting a session, linked shot, model, workflow or referenced look/profile returns `409 full_auto_in_use` while a nonterminal run or unresolved attempt depends on it. Identify affected sessions and offer Cancel followed by deletion after settlement. Protect cascade paths as well as direct routes. No new look-deletion API is required; guard supported domain deletion and retain session snapshots after library removal. Out-of-band dependency loss blocks `dependency_missing`, without silent substitution.

Creation/deletion and cancellation/deletion races must have one transactional winner. Stale workers must require a surviving run UUID, epoch and fence, not merely a reusable numeric session ID. Preserve loud folder-deletion failure reporting.

An old binary does not read a future PRAGMA user_version; that marker cannot make downgrade safe. Supported rollback uses isolated data: create a consistent pre-upgrade SQLite backup, stop/fence Full Auto, settle remote work (unresolved attempts block rollback), and retain the upgraded database/images intact. Start the previous release only against a separately restored pre-upgrade data/config directory, only after outstanding upgraded attempts settle. A rollback preflight must resolve data paths, refuse unresolved remote work, the upgraded directory or absent backup and not launch the old binary on refusal. New outputs remain in the retained upgraded directory, not the older snapshot. Directly launching an old executable against the upgraded DB is unsupported and cannot be retroactively prevented by this release.

## Risks / Trade-offs

- Legacy text lacks coverage and ownership facts -> require reusable profile setup; do not market all existing looks as immediately Full Auto ready.
- Additional profile storage creates a second identity -> bind exact source version/digest, immutable revisions and session evidence; never follow latest.
- Free-text semantic verification is incomplete -> retain evidence-backed blockers and inspectable prompts; automated approval is not a guarantee of semantic or visual perfection.
- Remote acknowledgement loss cannot provide exactly-once execution -> reconcile durable attempt identity or stop with a precise unknown-outcome remedy.
- Durable run ownership can conflict with manual controls -> service-level owner checks, explicit pause/edit path, race tests and one shared runner claim.

## Migration Plan

1. Create and verify a consistent pre-upgrade backup, then add profile, run, evidence/receipt and attempt tables transactionally; legacy rows retain their exact schemas and behavior. Deploy read support before enabling Full Auto writes.
2. Reuse pure look/progression candidate logic and add atomic opt-in creation. Expose profile readiness without changing old look versions or auto-populating inferred claims.
3. Add coordinator/runner recovery gates and UI; update README and matching docs. Old clients creating sessions without the added fields retain response/digest behavior.
4. Run full backend/frontend gates and isolated recovery journeys before enabling the entry point. Retain manual flow throughout.
5. Rollback: use Decision 12 isolated restore and refusal preflight, retaining the upgraded database/images. No in-place database downgrade or assumption that old code obeys a new schema marker is supported.
