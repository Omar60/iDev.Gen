## Context

Resources currently sends paths and explicit library keys. Creation writes session and one empty-take plan separately. Preparation routes pass no writer. The preparation writer is synchronous; backend.enhance is asynchronous and its historical structured output is flattened into prose.

The parser supports envelopes, lists, individual entries and auxiliary maps. Existing keys are caller-supplied. Required descriptive fields need authorized translations even when source text is English. Fused prose remains a complete descriptive input and may already specify pose, camera and wardrobe. Structural output validation cannot prove semantic continuity.

## Goals / Non-Goals

**Goals:** a complete file-to-reviewed-session journey, few normal inputs, actionable failures, existing contracts and reproducible results.

**Non-Goals:** resource Delete/Restore or purge; wardrobe progression without explicit user selection and approval; automatic fused-scene decomposition; semantic guarantees based on JSON keys; a second provider stack; implicit generation; a twenty-photo session cap.

## Decisions

### 1. Selected bytes reuse canonical import

Use a native multi-file input and raw uploads. Create a server-owned selection_id before uploads; its manifest owns file IDs, byte counts, effective targets, selection_revision and fixed expires_at. The lifecycle is open selection -> uploaded files -> preview -> committed or expired/cancelled. Reserve file count and bytes atomically across concurrent uploads, count actual streamed bytes, and roll back reservations for rejected/incomplete uploads. Every upload/removal/target change increments selection_revision and invalidates its preview. Preview and commit bind selection_id, revision, complete manifest digests and targets; cross-selection file IDs are rejected. Repeated commit returns the recorded result rather than importing twice. Atomically claim the selection/revision before canonical commit; two simultaneous requests cannot both enter import. The second receives active-operation status or the same committed result. Persist consumption/result consistently with import success; recovery after a crash must discover committed outcome rather than re-enter canonical commit. A rollback may release ownership for a fresh attempt but never allow simultaneous owners. The browser ignores responses for a superseded selection/revision. Expiry is 24 hours from selection creation, not extended by each upload. Stage exact bytes behind opaque server identifiers; never open a client path. Enforce 20 files, 10 MiB per file and 50 MiB per selection before expensive parsing, including aggregate limits across uploads. Expire staging after 24 hours and clean eligible content after commit. Keep physical stage paths out of browser payloads.

Reuse the canonical parser, fingerprints, attestation, duplicate accounting and atomic accepted-set commit. Keep path-backed canonical reports server-side with a safe browser projection. File/target changes invalidate preview; late preview responses cannot re-enable Import for a newer selection.

#### Browser selection HTTP contract

The new browser protocol is rooted at `/api/resources/import-selections`. Every new endpoint returns either the success body described here or `{"detail":{"code":"machine_code","message":"readable explanation","current":<optional current SelectionView>}}`. A `SelectionView` contains exactly `selection_id`, a JavaScript-safe integer `selection_revision`, `state`, RFC 3339 `expires_at`, ordered `files`, nullable `preview` and nullable `commit_result`. State is `open`, `committing`, `committed`, `cancelled` or `expired`; only `open` and `committing` are non-terminal. Each file view contains `file_id`, display-only `file_name`, `byte_count`, nullable `declared_library`, nullable `effective_library_key`, `matched_auxiliary_kinds`, nullable `effective_auxiliary_kind` and `status`. Preview contains an opaque `preview_token`, lowercase-hex `manifest_digest`, `committable` and the readable canonical report projection. Commit result is the safe canonical import result. Physical paths, device/inode values, nanosecond timestamps, raw fingerprints, attestation secrets and staged bytes never appear. Byte counts and revisions are guaranteed in `0..Number.MAX_SAFE_INTEGER`; every digest/token is a string. In particular, `mtime_ns` remains server-owned and is never round-tripped through JavaScript.

The routes are:

| Route | Request | Success |
| --- | --- | --- |
| `POST /api/resources/import-selections` | JSON `{"request_id":"client UUID"}` | `201` with a new `SelectionView`; replay of the same request ID returns `200` with the same view |
| `POST /api/resources/import-selections/{selection_id}/files` | multipart with exactly one `file` and one client `upload_id`; the file part bytes are staged unchanged | `201` with the current view and allocated `file_id`; same upload ID and byte digest replays with `200` |
| `DELETE /api/resources/import-selections/{selection_id}/files/{file_id}?expected_revision=N` | no body | `200` current view |
| `PATCH /api/resources/import-selections/{selection_id}/files/{file_id}` | JSON with `expected_revision` and one or both of `effective_library_key`, `effective_auxiliary_kind` | `200` current view |
| `POST /api/resources/import-selections/{selection_id}/preview` | JSON `{"expected_revision":N}` | `200` current view containing a fresh preview, including non-committable diagnostics |
| `POST /api/resources/import-selections/{selection_id}/commit` | JSON `{"expected_revision":N,"preview_token":"..."}` | `200` committed view/result; `202` committing view when another owner already holds the same valid commit |
| `POST /api/resources/import-selections/{selection_id}/cancel` | JSON `{"expected_revision":N}` | `200` cancelled view |
| `GET /api/resources/import-selections/{selection_id}` | no body | `200` current view; status reads also perform lazy expiry/recovery |

Selection-creation `request_id` values are globally unique; upload IDs are unique within one selection. Reusing either ID with different normalized metadata or different bytes returns `409 idempotency_conflict`. Mutations other than concurrent file upload require the exact current revision; stale revisions return `409 selection_revision_stale` with the current view. Uploads reserve one file slot and aggregate bytes while streaming, increment the revision only after a complete valid file enters the manifest, and return their resulting revision; the browser retains the highest received revision and ignores lower late responses. A file ID under the wrong selection returns `404 file_not_found` without revealing the other selection. Invalid target/kind or unresolved commit is `422`; per-file/aggregate/body limits are `413`; cancelled/expired actions are `410`; disabled writes are `503`. Cancel while `committing` returns `409 commit_active` because the canonical database transaction is not interruptible.

Preview tokens bind the exact selection/revision/manifest digest/effective targets and auxiliary kinds. Commit atomically claims that tuple with a server-only commit token and lease. A successful canonical resource transaction writes the recorded result in the same database transaction as accepted resources. A crash before that transaction leaves no import and lazy/startup recovery releases an expired claim back to `open`; a crash after commit always exposes the recorded result. A different commit tuple while an owner is active receives `409 commit_conflict`. Repeating the committed tuple before terminal metadata expiry returns the same result and never calls canonical import again.

Rejected alternatives: fakepath forwarding, frontend source parse/reserialize, and a second importer.

### 2. Identity defaults with explicit compatibility

Use valid top-level library as the normal target. Keys have 1-128 characters, no surrounding whitespace, ASCII controls, slash or backslash, and are not dot or dot-dot. Preserve spelling exactly. Filenames never determine identity.

An existing exact key is authoritative. If that key does not exist but canonical source ID/digest pairs overlap another stored library, preview requires explicit selection of an existing target or creation of a separate library. Multiple candidates remain an explicit choice. Similar names do not authorize merging.

Supported lists, single entries and auxiliary maps without an envelope remain uploadable. Missing/invalid declarations expose an advanced existing-library selector or explicit new key; do not force editing JSON. Choosing a historical target never renames it or mutates the source. Bind declared and effective identity to preview/commit and show the distinction. No persistent alias registry is needed. The browser adapter also recognizes envelope-like objects with an items list without a usable library field after explicit target selection. Expose has_entry_content_markers(data) for the existing marker set and reuse it in is_source_envelope and the browser adapter and, for this relaxed recognition only, allow no top-level keys except items and optional library; unknown keys such as random_payload remain unresolved. Already-supported canonical envelopes retain existing parser behavior. Extract items in memory for parsing while retaining original staged bytes/fingerprint and parser accounting. Ambiguous objects also carrying entry-content fields remain unresolved; do not silently discard them. Apply the same adapter at preview and canonical commit revalidation without rewriting source files or changing legacy parser/API defaults.

For auxiliary payloads matching multiple kinds (notably mined_families/mined_labels), require an explicit Advanced kind selection from the structurally matched candidates. Do not use first-shape-wins or filenames as authority. Record the chosen kind in the selection manifest/attestation and revalidate it against the same bytes at commit. Unsupported choices fail. Canonical service plumbing may accept explicit validated adapter context, but old callers without that context keep their current classification. This must preserve the existing attestation revalidation rather than patch only the browser report.

This compatibility exception replaces the previous unconditional ban on browser overrides. Unchanged path API/CLI remains available.

Show imported, needs translation, ready and needs source correction separately. Name blocked fields and link to their action.

Selected translation maps and editable source-backed rows both produce a direct translation_map and use the existing library bulk preview/apply endpoints with attestation. The single-revision translation endpoint is not an allowed shortcut for this UI. Reject excess with 413 before parsing or writes. Editable rows provide a no-LLM path. Suggest translations optionally uses the configured assistant for authorized descriptive fields only, preserving canonical keys and list order. Already-English required strings still need explicit sidecar entries; proposals may provide identity translations.

Proposals never write sidecars. Users edit/review, preview through canonical authorization, then explicitly apply against map digest and library fingerprint. Batch proposals at twenty source entries per action. Invalid/unsolicited fields are refused; stale responses after selection/library changes are discarded. Unknown mappings and malformed source fields require correction rather than a translation guess. Import commit never starts translation calls.

### 4. Four initial inputs and advanced options

Show character, one ready room scene, integer photo count from 1 through 500 (default twelve) and optional brief up to 2,000 characters. Preselect known character/scene. Default automatic when configured, otherwise manual with an inline Configure assistant action; users may explicitly select either mode.

Advanced contains look/wardrobe overrides, fixed/vary policy and raw take editing. Internally default all four dimensions to vary. A fixed dimension requires a non-empty user value. Assistant resolution of unspecified fixed dimensions is deferred; it is unnecessary for the default flow.

Twenty is the maximum takes per automatic preparation action, not a plan count cap. Larger sessions continue in consecutive batches. The 500-photo creation budget prevents accidental allocation of huge initial plans; validate it before building take IDs. Apply the same cap to new/growing authoring-v1 plans, while existing legacy/expert plans lacking authoring retain their established limits and remain readable/editable. Reject booleans, fractions and numeric strings as counts. Preserve valid existing manual/expert plans without authoring metadata.

Character means the existing model row. Guided creation resolves one effective workflow server-side: an explicit Advanced `workflow_id` wins; otherwise use the selected model's current default. The workflow must exist and pass the same graph/reference-slot compatibility checks required by resource preparation and submission. No default and no override is `422 workflow_required` before any write, with an action to assign a character default or choose Advanced. Guided creation persists the effective workflow on the session and creates a server-owned `authoring.workflow_binding` containing its ID, kind, canonical graph digest and canonical node-map digest. Those values participate in preparation input evidence, the automatic creative-input digest and copy-forward eligibility; the separately named effective_resource_input_digest remains resource/adaptation-only. A later change to the model default does not affect the session. Authoring-v1 sessions do not accept post-create workflow changes; a changed/missing workflow row or digest blocks new preparation/approval/submission with `409 workflow_changed` and requires a new session. Existing plans without authoring retain current workflow editing behavior.

### 6. Fused scenes keep a reviewed advanced path

Ready fused_scenes remain importable and inspectable but are excluded from simple automatic anchor choices. Provide Use advanced editor and Choose a structured scene. Preserve existing manual/expert fused workflows.

Show the entire authorized description beside effective shared/take choices. Contradictions require a separately stored user-approved adaptation or a different resource before finalization. Never split prose or drop its prompt automatically. Do not claim all contradictions are detectable.

Room descriptions can also contain arbitrary prose. Keep existing conflict gates, bounded writer instructions and final-prompt review. A valid four-key response proves structure only. Acceptance includes a fused camera/pose conflict and a writer placing another location inside pose; no structural-validator result may be advertised as semantic approval.

### 7. Atomic creation and existing transport

A dedicated `POST /api/sessions/guided` boundary accepts exactly `request_id`, `character_id`, nullable Advanced `workflow_id`, `scene_anchor`, `photo_count`, `brief`, `mode`, `variation_policy`, `look` and `initial_wardrobe`. The last four policy/override fields may be filled by defaults but are always explicit in the normalized request. It validates the character/effective workflow binding, count, brief, exact ready rooms anchor and policy and persists the idempotency record, session plus stable take IDs in one transaction before assistant calls. A new result is `201 {"session_id":N,"plan_revision":1,"plan":{...}}`; replay is `200` with the byte-equivalent stored result. Errors use `{"detail":{"code":"machine_code","message":"readable explanation"}}`; validation failures are `422`, assistant configuration is not required at creation, and transaction failure leaves no idempotency record or orphan session.

`request_id` is a globally unique client-generated UUID used only by guided creation. The server hashes the fully validated normalized request excluding `request_id` with canonical JSON. Inserting the request claim, session, plan and stored response is one serialized transaction. The same request ID plus the same digest returns the stored result after a lost response or concurrent retry. The same ID plus another digest returns `409 idempotency_conflict`. Two concurrent calls using one ID can create at most one session/plan. Different request IDs remain separate intentional creations.

Backend/frontend normalization retains authoring metadata. Older plans lacking it keep existing behavior and are not silently migrated. Async orchestration calls a field-preserving backend.enhance helper with existing settings/authentication/timeouts. Historical callers keep flattened output. Structured results pass through preparation validation and assistant provenance, never manual_completion disguised as assistant output.

Take output is limited to unlocked camera/framing/pose/expression. Fixed policy and explicit take values must agree or fail visibly. Neither can silently override the other, and per-take output cannot mutate resources, adaptations or shared state.

### 8. Ordered context and downstream edits

Process takes in stable plan order. Five predecessors support local variety, not global uniqueness. ### 9. Ownership, cancellation and recovery

Use a backend-enforced exclusive authoring claim per session shared by shared-state suggestions and automatic take preparation. Record operation identity, plan revision, ownership and recoverable lease/progress. No transaction spans a remote call. Concurrent requests return active progress rather than launch another call. Verify ownership and revision before accepting each response; renewed leases and fencing prevent expired owners from committing.

Persist each completed take. Stop on failure with completed/failed/remaining state. Cancel stops new scheduling and discards a late in-flight response. Reopening restores committed progress and offers Resume. After crash/expiry, completed snapshots are reused; incomplete remote calls may need retry. Exactly-once remote billing after response-before-persistence crashes is not promised.

Plan edits revoke old ownership; late output cannot overwrite new revisions. Bounded sequential requests and persisted progress need no new queue framework.

#### Persisted operation model and state machine

Persist one `authoring_operation` row per operation with opaque UUID `operation_id`, client UUID `request_id`, `session_id`, `plan_revision`, `kind`, canonical `request_digest`, `state`, monotonic integer `fencing_token`, `lease_expires_at`, ordered target IDs, completed result references, nullable failed item/error, remaining IDs, nullable kind-specific result, and timestamps. `kind` is exactly `shared_suggestions` or `prepare_takes`. A request ID is unique within its session and may be reused in another session. Non-terminal states are `active` and `cancel_requested`; terminal states are `succeeded`, `failed`, `cancelled` and `expired`. A partial unique constraint permits at most one non-terminal operation per session across both kinds. Terminal rows remain replayable evidence and are not reused for another request.

The server lease is ten minutes, deliberately longer than the existing five-minute assistant timeout. Only the backend owner renews it, transactionally immediately before each remote request and before scheduling the next item; status polling never renews ownership. Claim or resume increments `fencing_token`. A remote call runs outside a database transaction. Before persisting its response, one short transaction requires all of: matching operation ID/token, `active` state, unexpired lease, unchanged plan revision, unchanged request inputs and current resource/workflow validity. It then persists the take/evidence and progress together. Any failed predicate discards the response. No transaction remains open across network I/O.

The HTTP surface is rooted at `/api/sessions/{session_id}/plan/authoring/operations`:

| Route | Request | Success |
| --- | --- | --- |
| `POST .../operations` | `{"request_id":"client UUID","expected_revision":N,"kind":"shared_suggestions|prepare_takes","take_ids":[...]}`; `take_ids` is absent for suggestions and a non-empty stable-order subset for preparation | `202 OperationView` for a new active operation; `200` for an idempotent active/terminal replay |
| `GET .../operations/{operation_id}` | no body | `200 OperationView`, including terminal state and recoverable progress |
| `POST .../operations/{operation_id}/cancel` | `{"expected_revision":N}` | `202` while an in-flight response must be discarded; `200` when terminal or immediately cancelled |
| `POST .../operations/{operation_id}/resume` | `{"expected_revision":N}` | `202` after a new fenced lease; `200` if already active/succeeded |
| `POST .../operations/{operation_id}/accept` | for a succeeded `shared_suggestions` operation only: `{"expected_revision":N,"accepted":{"look":<optional string>,"initial_wardrobe":<optional string>}}` | `200` new plan revision and accepted evidence; identical retry returns the stored acceptance result |

`OperationView` contains exactly `operation_id`, `session_id`, `plan_revision`, `kind`, `state`, `created_at`, `updated_at`, nullable `lease_expires_at`, `progress`, nullable `result`, nullable `error`, `can_cancel` and `can_resume`. `progress` contains `requested`, ordered `completed`, nullable `failed` (`take_id` plus one readable error) and ordered `remaining`; it exposes no owner or fencing token. Suggestion results expose validated pending proposals but do not mutate the plan. Prepare results reference persisted snapshots and never echo credentials or full provider errors.

The standard new-endpoint error body is `{"detail":{"code":"machine_code","message":"readable explanation","operation":<optional OperationView>}}`. Missing session/operation/take is `404`; malformed kind/targets are `422`; disabled start/resume/accept is `503`; no assistant for an automatic action is `409 assistant_unavailable`; stale plan is `409 plan_revision_stale`; another request while a different operation owns the session is `409 authoring_active` and includes its view; reused request ID with a different digest is `409 idempotency_conflict`. Status and idempotent replay return terminal expired state with `200`; resume of an expired/failed/cancelled operation is allowed only while its original plan revision and inputs remain current. A succeeded operation is never rerun. Suggestion acceptance is a separate plan CAS: only the succeeded operation's validated output may be accepted, edited values are stored accurately, and the operation stores acceptance digest/result so a lost `200` can replay while different acceptance content conflicts. A revision change fences the operation, records it `cancelled` with `plan_revision_changed`, and makes resume or uncommitted acceptance return stale conflict.

Cancel changes `active` to `cancel_requested`; no next remote call may start. The owner discards any late response and commits `cancelled`. If no owner returns, lease recovery converts expired `cancel_requested` to `cancelled` and expired `active` to `expired`. A failed take commits completed references, the one failed item and remaining IDs as `failed`; Resume retries from that failed item without regenerating completed ready/generated takes. Response-loss retries use `request_id`: the same normalized start returns the same operation, while another body conflicts. Exactly-once provider billing remains explicitly unavailable for a crash after provider response and before the fenced persistence transaction.

### 10. Personal looks reuse appearance and garment building blocks

A personal look is a named reusable preset containing optional appearance text (hair, makeup and styling), an optional outfit referencing an ordered set of garment records, and provenance. It does not contain character identity, camera, scene, place or lighting. Those remain selected separately. The normal session screen offers an optional Saved look picker in the shared summary, not another mandatory initial field.

Reuse garment/outfit concepts and catalogue reads, but do not delegate Looks writes to /api/wardrobe/import. That legacy endpoint writes as it iterates and skips existing keys without content equality checks. Add a Looks preflight that validates the entire payload and resolves conflicts, then rechecks state and performs all writes in one transaction. Reuse lower-level persistence only where it can honor that transaction; leave legacy import semantics unchanged. Add the smallest persistent saved-look wrapper needed to associate appearance and an outfit. Keep personal looks separate from immutable mined asset_revision payloads. A garment has stable identity, complete worn wording and optional moved-aside wording. Do not require rigid body-part slots: one-piece garments and multiple layers must work. Removable accessories belong with garments, never in constant appearance. Clothing accidentally embedded in free appearance text must be editable and flagged for review; do not claim perfect semantic detection.

Create forms hide technical keys and let users name a look, add/reuse garments, reorder their removal order and save. Store new immutable preset versions (or new immutable records linked to a logical look); editing never mutates a previously used snapshot. Existing legacy garment/outfit keys are not reworded: saving changed clothing uses new records/keys. Do not expand this work into general catalogue deletion or lifecycle management.

Selecting a look copies its appearance, garment wordings/order and stable preset ID/version/digest into the plan with origin metadata. The copied content is authoritative for that session, not a live catalogue lookup. An appearance-only preset leaves wardrobe unchanged; absence of an outfit is not a garment-free instruction. Existing explicit overrides require an explicit Replace or Keep decision; selecting a preset never silently discards them. Future preset edits affect only new selections. Updating an existing session requires an explicit CAS application with ordinary invalidation/freeze rules.

### 11. Text, JSON and photo inputs converge on the same editor

Support manual creation and browser-selected JSON import/export. Use the closed portable-look-v1 envelope and conflict rules in specs/resource-store/spec.md, converting its garment_keys to the complete ordered snapshot defined by session-plan; no machine paths, embedded photos, credentials or session data. Export text plus provenance-safe identifiers, not private image locations. Accept existing garments/outfits JSON as an outfit-only import, then allow saving it as a named look. Prevalidate all references, duplicate keys and content before any write. Identical re-import is a no-op; differing content under the same logical identity requires explicit new-version/save-copy resolution, never silent overwrite or skip. Preview and commit are bound to the reviewed content. Persist an atomic server-owned receipt binding original portable identity and pre-remap portable_content_digest to destination identity and garment/outfit mapping; repeated original envelopes resolve to the same version before allocation, including explicit new-version/save-copy imports. Export keeps local keys and its own canonical equality path. Follow resource-store receipt uniqueness and inconsistency rules. Limit actual streamed HTTP body bytes to 10 MiB before JSON/Pydantic deserialization on all look preview/import/commit endpoints receiving JSON content, including the legacy garment/outfit input accepted here. Count bytes even when Content-Length is missing or false; return 413 before parsing or writes.

Photo import accepts one JPEG, PNG or WebP at a time, at most 10 MiB decoded file bytes, through a validated upload boundary with opaque IDs. Reuse the configured vision transport/model, but add actual Pillow verification/decoding for this boundary. Existing enhance._check_image checks data-URI spelling and estimated size only. Verify supported file format, dimensions (at most 25 megapixels), actual bytes and complete decode before inference; reject malformed/truncated and oversized images. Pillow is already a backend dependency. Filename is metadata only. Selecting a photo stages it privately and shows Extract look; only that explicit action sends it to the configured assistant. No provider/configuration stack is added.

Extraction proposes editable appearance and individual visible garments, and leaves the removal order for user confirmation. Do not infer unseen garments, identify the person or import background/pose/camera as look identity. Unknown details are marked unresolved for review; users may omit them explicitly. No vision-capable assistant means extraction is unavailable with an explanation, while the photo preview and manual form remain usable. Vision failure or invalid structured output saves no look. Extracted text uses the existing English output convention.

Photo extraction has a stricter capability predicate than text authoring. It is available only when the ordinary assistant endpoint/model are configured and `llm_vision_model` is non-empty. Setup populates that field only from a model whose provider capability response or existing family fallback marks it vision-capable; an operator-written non-empty config value is an explicit local declaration but still fails visibly if the provider rejects images. When the ordinary `llm_model` is itself detected as visual, Setup stores that same ID explicitly in `llm_vision_model`. Extraction never falls back from an empty vision model to the text model. Empty vision configuration returns `409 vision_unavailable` before staged content is sent, with actions to configure a verified vision model or continue manually. Provider refusal or invalid visual output is `502 vision_request_failed`, saves no look and retains the temporary preview until cancel or expiry so configuration can be corrected and extraction retried.

Save only after explicit review; persist a redacted request projection: exact text messages/structure, model identifier and non-secret generation parameters, replacing the image content part with its SHA-256 digest, media type, byte count and dimensions. Preserve validated output and user corrections. Never persist a raw data URI, image bytes, endpoint credentials or secret headers in provenance. This records the request evidence excluding binary content, not the exact wire request; replay does not re-run inference after the image expires. Staged photos expire after 24 hours and are removed after save/cancel when no longer needed. A saved look remains reusable without the image or another assistant call. This is text extraction, not a generation reference: never auto-attach the photo to ComfyUI or promise visual clothing/identity fidelity.

### 12. Explicit progression materializes existing wardrobe changes

Keep wardrobe constant by default. Offer Plan clothing changes for a selected snapshotted outfit. The user confirms garment removal order, selects the final stage and start/end take boundaries, and previews every resulting wardrobe. Use a pure derivation accepting the complete look_snapshot.outfit as an argument. Do not call arcFor(outfitKey): it reads live globals and silently filters unknown keys. Reject incomplete, duplicate or inconsistent snapshot garment identities before deriving; no missing garment may disappear silently. Reuse only established outfit arc semantics, including an optional moved-aside stage only when the final garment has such wording. No model decides order or invents garments. Do not persist a reusable preset's derived stage list; derive it from its snapshotted garments.

For a requested sequence of K stages across M selected consecutive takes, require M >= K (for K > 1) and preview stage floor(i * (K - 1) / (M - 1)) for zero-based take offset i. K = 1 means constant clothing. Fewer takes require choosing fewer stages or a wider interval; do not silently skip a garment state. Before the interval keep the initial wardrobe; after it carry the selected final stage. The user may edit boundaries before applying and need not choose a fully removed final state.

Apply the reviewed preview in one plan CAS mutation as initial_wardrobe plus minimal from_here events keyed to stable take IDs; keep the existing this_take option for local overrides. Existing events require an explicit replace/merge review and no duplicate take events. The approved explicit events, not a live auto-distribution rule, remain authoritative after reordering or adding takes; re-run the planner only on user request. Store the source preset snapshot and approved planner inputs as provenance, not a second effective-wardrobe truth.

Each take prompt states only garments still worn, repeating unchanged garment wording exactly. Do not append the original full outfit elsewhere in look or take synthesis. A deliberately empty outfit uses an explicit no-clothing sentence; an empty string keeps its existing no-description meaning. This prevents removal from becoming a contradictory positive description. Shared appearance stays constant. Existing source-clothing conflicts require adaptation or another resource. Use the exact canonical wearing rule in specs/resource-prompts/spec.md for both initial_wardrobe and all stages, including deterministic punctuation and the explicit empty-state sentence. Backend application and frontend preview must agree byte-for-byte; reuse existing arc semantics without importing legacy catalogue measurement gates into resource-v1.

### 13. Review ends preparation

Show effective photo choices and status with Edit/Prepare/Resume; put prompts and provenance in expandable details. No revision IDs or four-field typing are normal prerequisites. Reuse explicit review approval, submission and runner gates with labels distinguishing text preparation, queueing and generation. Offer a reviewed test subset before the full session. Preparation never approves, submits or runs.

### 14. Startup and lazy recovery clean transient state

Use no scheduler or queue framework. On every application startup, run a bounded recovery sweep before serving requests. It marks every `active` authoring operation from the prior process `expired`, every prior `cancel_requested` operation `cancelled`, and preserves completed progress for Resume. It also releases stale browser-import `committing` claims with no atomic commit result back to `open` when their fixed selection expiry has not passed, expires overdue import selections/photo stages, and removes eligible staged files. A committed resource transaction and its selection result are atomic, so recovery never infers import success from resource rows.

Every selection/operation/photo GET or mutation first performs lazy recovery for that record and a bounded opportunistic sweep, using injected UTC time in tests. Authoring leases expire according to their ten-minute deadline; import selections and photos expire exactly 24 hours after creation and activity does not extend them. Import commit and selection cancel remove staged bytes after the terminal database state is durable. Photo save/cancel removes bytes after saved redacted provenance or cancellation is durable. Expiry removes bytes and marks a tombstone; terminal selection result/status metadata remains readable until 24 hours after `expires_at`, then may be purged and return `404`. An expired retained record returns `410` for mutation and `200` terminal status. Authoring operation rows and prepared provenance remain durable history under existing session deletion rules.

Cleanup never deletes committed resources, saved looks, plans, prepared snapshots or generated history. A filesystem cleanup failure is recorded and returned as a readable warning while the database record remains terminal and retryable by later sweeps; it is never reported as successful deletion. Private physical paths remain logs/server diagnostics only.

### 15. Feature flag and downgrade preserve authoring metadata

`resource_planning_enabled=false` continues to block new resource-v1 creative writes with `503` while preserving reads and delivery/execution of already prepared and approved snapshots. It additionally blocks all new selection POST/PATCH/DELETE routes (including upload, preview and commit), translation-proposal generation/application, guided creation, generic authoring plan saves, suggestion start/resume/accept, automatic or manual authoring preparation, adaptation writes, dependency refresh, review approval, saved-look create/edit/import, photo stage/extract/save, preset application and wardrobe-progression application. Existing translation write gates remain. The existing path-backed import API/CLI and legacy garment/outfit import keep their prior flag behavior because this change does not redefine those compatibility tools.

Read-only resource/list/detail/readiness/session/plan/review/recovery/selection-status/operation-status/look/photo-preview endpoints remain available. Selection or authoring cancellation remains available as a safety action while disabled. Disabling during a remote call prevents another call; the fenced response transaction detects the flag, discards late output and records the operation cancelled with `feature_disabled`. Existing idempotent Submit and runner execution remain available only for snapshots that were already ready and authoritatively approved before disablement; no new approval or preparation can manufacture eligible work.

Operational downgrade is supported only to a rollback-compatible binary that understands this flag. While the new binary is still running: create and verify the existing SQLite backup, persist `resource_planning_enabled=false` (or guarantee the environment override for the target process), cancel or observe terminal all active authoring operations, verify the disabled state, then stop the process cleanly. Start the older binary with the flag still disabled and inspect authoring plans/snapshots read-only. Do not re-enable writes until a binary that understands the closed authoring schema is restored. A target predating the flag is not allowed to open the upgraded database for writes; restore the verified pre-upgrade backup instead. Additive tables/columns remain untouched. Blocking generic plan saves is the guard that prevents an older normalizer from dropping unknown `authoring` metadata.

## Risks / Trade-offs

- Arbitrary prose may contradict shared state: preserve visible review and honest limits.
- Suggestions add assistant calls: make them explicit, bounded and reviewed before writes.
- Conservative invalidation repeats some work: disclose affected takes and preserve history.
- Simple rooms-only anchors exclude some mined scenes: keep the advanced path discoverable.
- Historical renames cannot always be inferred: retain explicit compatibility targeting.
- Ownership adds recovery state: test races, cancellation, expiry and stale responses.
- Photo extraction can omit or misdescribe garments: require editable review and never treat an inferred item or removal order as accepted.
- Preset edits could change old sessions: copy exact content on selection and verify sessions remain unchanged after library edits.
