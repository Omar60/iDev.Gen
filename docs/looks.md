# Saved looks

The **Looks** view (`#/looks`) is a manual editor for reusable appearance and
optional outfit details. Look and garment identities are generated by the
server and hidden from the form.

## Create and revise a look

Choose **Create look**, enter a name, and optionally describe constant
appearance such as hair or makeup. Review that text for clothing: the editor
reminds you to move removable items into the outfit, but it does not detect or
move clothing automatically.

An outfit is optional. Choose a saved outfit or build one from existing or new
garments. Edit each garment's wording for how it is worn and, optionally, how it
is moved aside. Reordering or removing garments changes only the new version.
Changing a saved garment's wording creates a new identity, preserving its
existing catalogue row and older versions. The list has no body-part slots, so
it can represent one-piece clothing, layers, and accessories.

Saving a new look creates version 1. Saving edits creates another immutable
version; use **Version history** to inspect earlier versions. Each saved version
contains its complete garment wording and order, so it remains readable if the
live wardrobe catalogue later changes or an item is retired. A name-only edit
can have the same content digest as the prior version because the digest covers
appearance and outfit content, not the name or version number.

When a version has no saved outfit, its `outfit` is `null`. That only means no
separate outfit was saved: appearance text may still describe clothing, so
review it manually.

## Archive a look

Choose **Archive** beside a saved look and confirm the action. The look leaves
active lists and selectors, but all immutable versions, profile and photo
evidence, import receipts, and session snapshots remain stored. Exact version
reads and exports remain available, and active Full Auto work keeps its bound
look and profile. New versions, profile writes, or imports targeting the
archived identity are rejected. Archiving cannot be undone from the current UI;
there is no archive browser or restore action.

## Current scope

The **Looks** view (`#/looks`) includes reviewed JSON import, selected-version
export, and one-photo staging. Its history selector stays bounded to the first
20 versions plus the latest and currently selected version; enter any positive
exact version in **Version number** to load it directly. Export downloads the
selected version's portable JSON bytes.

JSON import previews local mappings and remaps before commit. When a conflict
requires a choice, select an explicit import, new-version, or copy option first.
A legacy outfit import adds catalogue garments and outfits only. Choose an
imported outfit with **Start a look from this outfit**, review it in the editor,
then save to create a named look.

**From photo** stages one JPEG, PNG, or WebP for preview. Describe it manually,
or extract an editable proposal when Setup confirms a configured text assistant
and explicit vision model. Review the appearance and garment list, correct or
omit every unresolved detail, and confirm garment removal order before saving.
Manual save remains available when extraction is unavailable. Cancel the stage
or refresh its status; if cleanup reports a warning, retry cleanup from the
view. This photo input describes a saved look and never becomes a generation
reference.

With MiniMax, `MiniMax-M3.1-Flash-Preview` can be used as both the text and
explicit vision model when the key has access. The transport separates provider
reasoning from JSON output; it does not extract JSON from prose or accept
partial objects. See [Setup](getting-started.md#setup) for model selection.

## Prospective automation suggestions

The backend can prepare editable automation suggestions before a look is saved.
This operation creates no look version, accepted profile, garment identity,
outfit, or session. Suggestions do not accept their own facts or choose garment
order. Keep uncertain ownership as `null` and uncertain coverage as `unknown`;
the assistant never decides the all-garments-absent baseline or inventory
completeness.

For a manually entered draft, call `POST /api/looks/automation-proposals` with
the exact current appearance and ordered garment definitions:

```json
{
  "appearance": "Short dark hair and a silver necklace.",
  "garments": [
    {"key": null, "wording": "a white shirt", "aside": "the shirt folded over one arm"},
    {"key": "existing-garment-key", "wording": "blue jeans", "aside": ""}
  ]
}
```

The response includes an opaque `proposal_id`, `draft_content_digest`, the
prospective profile, a safe `request_projection`, and `expires_at`. The digest
binds schema version 1, the exact appearance, and the exact ordered garment
definitions, including any existing key supplied by the form. It identifies
this pending draft; it is distinct from the saved look's final `content_digest`,
which is computed from its immutable appearance and outfit snapshot after
server-assigned identities exist.

The prospective profile is a closed object with `schema_version`,
`draft_content_digest`, `appearance_segments`, `garment_coverage`,
`baseline_coverage`, and `inventory_complete`. Appearance segments partition
the original text using zero-based, half-open Unicode scalar offsets. An owner
is `permanent`, `null`, or `{"garment_index": n}`. Coverage entries use the
same ordered garment indices and `worn`/`aside` states; each state records
`chest`, `hips`, `legs`, and `feet` as `full`, `partial`, `none`, or `unknown`.
The provider must leave baseline and inventory completeness `null`. The exact
source list and indices let the server map reviewed facts to the final saved
garment keys later, including a new key when wording changes.

Manual proposals and their source digest, validated candidate, and safe request
projection are usable for 24 hours. Expired records are purged on lookup or the
next proposal request. The projection contains the
configured model, allowed request parameters, and a digest of structured
messages; it does not retain endpoint text, credentials, prompt text, or image
bytes. Expired proposals cannot be reused.

Photo extraction keeps its historical `{}` request and response shape. To opt
in, call `POST /api/looks/photo-stages/{photo_id}/extract` with
`{"include_automation": true}`. The response keeps the ordinary appearance,
garment, uncertainty, and proposal fields and adds `automation`. A ready
companion contains the ordinary photo proposal ID, a server-computed
`draft_content_digest`, and a prospective profile. The provider returns no
digest: the server attaches it only after validating the exact ordinary
appearance and ordered garment list. If the ordinary photo proposal is valid
but the companion candidate is malformed, extraction retains that look
proposal and marks automation `unavailable`. If the combined provider request
fails, extraction retries the historical ordinary request and returns a valid
look proposal with automation `unavailable`. An invalid ordinary proposal keeps
the existing extraction error behavior. The photo companion and its redacted
request evidence expire with the existing staged proposal; neither image bytes
nor a data URI are included in that evidence.

The current browser editor does not yet show this combined automation review or
save. Users can continue to describe and save ordinary looks manually; the
prospective API leaves any suggestions unaccepted for a later review.

In **Shared Choices** on an authoring-v1 session, load an exact saved-look
version, explicitly choose which appearance and wardrobe fields to replace or
keep, and apply it through the plan revision CAS. The selected version is copied
into a session snapshot, so later edits to the saved look do not change that
session. **Plan clothing changes** reviews a progression from that snapshot and
applies it through a signed preview and plan CAS. See
[applying a saved look](sessions.md#applying-a-saved-look) and
[previewing a saved-look outfit progression](sessions.md#previewing-a-saved-look-outfit-progression).

### Reusable automation profiles

In **Looks**, expand **Reusable automation profile** on an exact saved-look
version. Load a selected immutable profile revision as the editing basis, or
start a blank draft; publishing creates the next revision for that same look
version. The selector shows server readiness and the reasons an incomplete
profile needs attention. An incomplete profile may still be applied for its
permanent appearance projection when the current-plan API checks and accepted
appearance ownership validate the exact profile. It supplies no derived
coverage; existing manual coverage remains user-authored.

The exact-revision selector in Resources is read-only: it shows readiness
diagnostics but does not open the profile editor. To correct a profile, open
**Looks** from the main navigation, edit and publish a new immutable revision
for the exact saved-look version, then return to Resources and select that
revision explicitly.

For each appearance phrase, select the saved text and assign it to permanent
appearance or a progressive garment. The source text stays unchanged; the view
shows the joined permanent projection used by profile-aware application. The
**All appearance is permanent** shortcut previews and asks you to confirm that
assertion for the exact version.

Record chest, hips, legs, and feet as full, partial, none, or unknown for the
baseline (every listed garment absent) and each garment's worn and, when
defined, moved-aside state. A blank draft has unknown coverage, no baseline,
and no inventory assertion. Confirm explicitly whether the listed garment
inventory is complete. Unknown is not none, and garment prose does not supply
coverage facts. You can publish an incomplete profile, but Full Auto readiness
requires a confirmed complete inventory and known applicable facts. Coverage
is recorded once in the reusable profile instead of repeated per take.

The **No coverage in supported regions** shortcut applies only to states you
select, after preview and confirmation. It asserts `none` for the four listed
regions and does not confirm inventory completeness.

To reuse coverage, select an exact source version and profile revision, map
source states to target states, preview, and confirm the copy. Mapping between
states within the same exact look version is an explicit user assertion that
those states are equivalent. Across look versions, only the same state copies,
and only when the garment key, canonical wording, and state wording are
unchanged. The accepted source profile digest is retained as provenance;
changed or unaccepted states remain unknown, and appearance ownership spans
are never copied.

In **Shared Choices**, you can explicitly apply an exact profile revision to an
authoring-v1 plan with the required replace/keep decisions. The write uses the
current plan revision, then reads the saved plan back; a linked shot freezes
the selected profile identity. Application updates the plan and its eligible
stage coverage. It does not start a progression, prepare or review takes,
submit them, or run the session. The profile covers only the four named regions
and does not guarantee rendered pixels. Portable look-v1 JSON does not include
profiles.

### Automation profile storage

The backend can store a separate immutable v1 automation profile for an exact
saved-look version. Its closed object contains `schema_version`, `look`
(`key`, `version`, `content_digest`), `appearance_segments`,
`garment_coverage`, `baseline_coverage`, `inventory_complete`, and
`authored_provenance`. `content_digest` binds the profile to the saved version's
canonical `{appearance, outfit}` content. Publishing adds a `profile_revision`
and canonical `profile_digest`; it requires the expected look digest and prior
profile revision, so stale or competing writes fail.

Each appearance segment records `segment_id`, `start`, `end`, `text`, `owner`
(`permanent` or `garment:<key>`), and provenance. Offsets are zero-based,
half-open Unicode scalar indices; `text` must match that exact slice, with no
normalization. Segments partition the saved appearance without gaps or rewriting
its text. Coverage is keyed by an outfit garment and optional `worn`/`aside`
state; each state has `regions` (`chest`, `hips`, `legs`, and `feet`, each
`full`, `partial`, `none`, or `unknown`) and `provenance`.
`baseline_coverage` has the same shape or is `null`. `inventory_complete` has
`value` (`true`, `false`, or `null`) and `provenance`. Every provenance object
records `origin` (`user` or `reviewed_structured`), `source_identity`,
`source_digest`, and the profile's `accepted_revision`.

Missing states and explicit `unknown` values are valid stored facts; profile
storage alone does not establish readiness. The internal exact-version check
keeps manual look use available, but reports a profile ready only when its
applicable facts have accepted provenance, every required region is known, and
inventory is confirmed complete. Reviewed facts must resolve an immutable
source profile and match the same fact; missing, changed, or unverifiable source
evidence is not accepted.

For looks with an outfit, baseline coverage that says any supported region is
fully or partially covered conflicts with the garment-free end of the
progression. An appearance-only look has no such progression conflict, but it
still needs explicit accepted baseline and inventory facts. Readiness is limited
to chest, hips, legs, and feet. For structured coverage, `partial` means some
but not all of the named region; it does not identify a side or subregion, and
two partial layers do not combine into full coverage. V1 does not structure
arms, hands, back, or finer subregions; use manual authoring when those details
matter.

Reviewed reuse requires an explicit selection. A garment state copies only
when its key, canonical wording, and selected `worn` or `aside` wording are
unchanged. Baseline copies only when the complete appearance and outfit are
unchanged. The copy contains coverage regions and source provenance; it does
not copy inventory confirmation or appearance ownership spans. Missing,
changed, or unaccepted facts must be asserted again for the target profile.
Source-profile validation follows at most 32 provenance levels; deeper or
unverifiable chains require a fresh explicit user assertion.

Accepted ownership spans can project only explicitly permanent clauses into a
profile-aware session's constant appearance; progressive clauses remain owned
by wardrobe stages, while the complete saved-look version stays as source
evidence. Session evidence binds the projection to the exact look and profile
revisions. The browser selection helper maps UTF-16 selection offsets to the
same Unicode-scalar spans used by the backend, including emoji and combining
marks, without normalizing the source text.

When the applied profile is ready, session application derives each take's
coverage from its matching progression stage and records immutable evidence for
the exact look, profile, ownership, stage, and compiled text. Prepared evidence
consumes that record. Editing derived coverage clears the claim for that take in
the new plan revision and invalidates dependent preparation; unchanged takes
retain eligible copy-forward, and earlier revision and linked-shot history stay
unchanged. An incomplete profile does not replace or certify manual coverage;
the existing manual coverage and workflow remain usable.

During finalization of a session with an applied profile, the server checks
effective positive inputs—including the model trigger and base prompt, projected
look and coverage, resolved resource/adaptation text, and take or writer
clauses—for exact accepted worn wording or garment-owned appearance clauses
that conflict with a candidate stage for the materialized wardrobe. A corrected
adaptation replaces its source text; the exact accepted aside phrase remains
valid. When identical wardrobe text maps to multiple stages, the check evaluates
each candidate without guessing an index or redistributing progression. A
detected conflict blocks finalization.

This is a literal wording check: negations and object mentions can match, while
paraphrases can be missed. It is limited text evidence, not semantic or pixel
verification, and it never silently rewrites or deletes source text.

### Automation profile API

`GET /api/looks/automation-profiles` reads one immutable revision. Its query
must contain exactly one each of `look_key`, `version`, `content_digest`,
`profile_revision`, and `profile_digest`; it returns that exact profile, including
historical revisions. There is no implicit latest-profile lookup.

`POST /api/looks/automation-profiles` creates the next immutable revision. Its
closed JSON object contains exactly `look_key`, `version`, `content_digest`,
`expected_profile_revision`, and `profile`. The look identity must match the
saved version; use `expected_profile_revision: 0` for the first revision and the
current revision for an update. The response returns the canonical profile with
its assigned `profile_revision` and `profile_digest`. The revision check is
compare-and-swap: one concurrent writer can succeed, and stale writers must
reload before retrying.

`GET /api/looks/{look_key}/versions/{version}/automation-profiles?content_digest=...`
discovers profile revision/digest identities and server readiness for that
exact look version. It does not select or return a latest profile; choose a
revision explicitly, then use the exact-identity read above.

`POST /api/looks/automation-profiles/copy-preview` accepts exact source and
target identities plus selected state mappings, and returns copied and skipped
facts without writing a profile. Review that response before publishing a new
profile revision; stale source or target identity is refused.

`POST /api/sessions/{sid}/plan/apply-automation-profile` explicitly applies an
exact saved-look and profile identity to an existing authoring-v1 plan. Its
closed body contains `expected_revision`, `look_key`, `version`,
`content_digest`, `profile_revision`, `profile_digest`, and `decisions`.
`decisions` explicitly chooses `replace` or `keep` for `look` and, when the
outfit or existing plan requires it, `initial_wardrobe`; profile application
requires `look: "replace"`. The route checks both the exact look/profile
identity and plan revision before writing. Success returns the new
`plan_revision` and `conflicts`. A stale plan, changed profile, linked-shot
identity freeze, or other plan conflict is refused without applying the request.
This operation only updates the plan; it does not authorize preparation
or generation.

`GET /api/sessions/{sid}/plan` includes `profile_application` only when the
current plan revision has an applied profile. The field contains only
`look_key`, `version`, `content_digest`, `profile_revision`, and
`profile_digest`, providing a safe identity readback after an uncertain write.

These routes return errors in the stable
`{"detail":{"code":"...","message":"..."}}` envelope. Codes identify
invalid requests, stale identities/revisions, missing records, disabled
resource planning, and plan conflicts; messages do not expose private source
values, filesystem paths, or internal exception text.

The Looks view edits reusable profiles, and Shared Choices can explicitly
apply an exact revision to a manual authoring-v1 plan. Guided creation can
apply an exact saved-look snapshot through
`POST /api/sessions/guided`, without applying a profile or starting progression.
Full Auto preflight and selection/consent are available in Resources; its
persisted progress and Cancel/Resume controls are available on the Session
page.
The manual saved-look workflow remains available, including progression
preview, review, submission, and Run controls. See the
[guided creation API](sessions.md#saved-look-and-full-auto-creation-api).
Portable-v1 JSON continues to exclude profiles, so automation readiness does
not transfer on import or export.

## Temporary photo staging API

`POST /api/looks/photo-stages` accepts exactly one `multipart/form-data` file
part named `file` and returns `201` with an opaque `photo_id` and stage status.
The server identifies JPEG, PNG, or WebP from the bytes, verifies the complete
container (including PNG chunk checksums), and fully decodes one frame with
Pillow. Trailing data is refused; client filename and declared MIME type are not
trusted. The actual file is limited to 10 MiB and 25 megapixels. Multipart
framing has a separate 64 KiB allowance.

The stage can be previewed and checked before a caller submits the same JSON
fields accepted by `POST /api/looks` to the save endpoint. Those fields remain
manual and reviewed. See the extraction endpoints below for the assistant
proposal path. Repeating a save with identical content returns the stored
result; a different payload for an already-saved stage returns `409`. Saving
creates the look without retaining the staged image as look content.

Expiry is fixed at 24 hours after creation and does not extend on access. A
terminal stage status is retained for 24 hours after its original expiry and may
be purged after that when cleanup succeeds; failed cleanup can keep it available
longer. Status returns `200` for a retained terminal stage; an expired stage's
preview, save, or cancel returns `410`, and a purged ID returns `404`. Save and
cancel persist their terminal state before deleting staged bytes. If cleanup
fails, status includes `cleanup_warning`; a later stage access retries cleanup.
A cleanup warning does not undo a saved look. With resource planning disabled,
stage creation, extraction, and either save return `503`; status, preview, and
cancel remain available.

## Photo extraction and review API

`POST /api/looks/photo-stages/{photo_id}/extract` accepts an empty JSON object
and asks the configured vision model for visible general appearance, garment
candidates, and unresolved details. The response contains a stage-bound
`proposal_id`, `appearance`, `garments`, and `unresolved` items with IDs such as
`u1`. Garments are candidates, not an accepted or ranked outfit. Extraction
requires both the configured assistant endpoint/model and an explicit
`llm_vision_model`; otherwise it returns `409 vision_unavailable`.
If the provider fails or returns an invalid proposal, extraction returns `502`,
saves no look, and leaves the stage available for preview until its normal
expiry.

Review the proposal and submit it to
`POST /api/looks/photo-stages/{photo_id}/save-extracted` with the proposal ID,
look name, edited appearance, the complete ordered `garments` list, and one
`unresolved_decisions` entry per unresolved ID. Each garment is an object with
`wording` and optional `aside`; these are new garment definitions, with no
client-supplied catalogue keys. Each decision must either use
`action: "correct"` with correction text included in the reviewed look, or
`action: "omit"`. Set both `review_confirmed` and
`removal_order_confirmed` to `true`; the server rejects incomplete decisions,
unconfirmed review, stale proposals, and attempts to save a successful proposal
through the manual save endpoint. If extraction did not produce a successful
proposal, the existing `/save` endpoint remains available for manually entered
look fields.

For example, this request corrects `u1` with wording included in a garment:

```json
{
  "proposal_id": "0123456789abcdef0123456789abcdef",
  "name": "Blue shirt",
  "appearance": "Long dark hair tied back.",
  "garments": [
    {"wording": "a blue cotton shirt", "aside": "unbuttoned at the collar"}
  ],
  "unresolved_decisions": [
    {"id": "u1", "action": "correct", "correction": "blue cotton shirt"}
  ],
  "review_confirmed": true,
  "removal_order_confirmed": true
}
```

Saving commits the immutable look version, photo evidence, and saved-stage
receipt in one transaction. Staged photo bytes are cleaned up after that commit.
`GET /api/looks/{key}/versions/{version}/photo-evidence` returns the
source SHA-256, media type, byte count and dimensions, the sanitized request
projection, the assistant proposal, and the reviewed corrections. The request
projection records the exact textual messages, model, and generation parameters
(`temperature`, `stream`, `response_format`, and `reasoning_effort` when sent),
but replaces the image data URI with source metadata. It excludes the provider
endpoint, headers, credentials, and photo bytes or URI. This route returns
`404` for versions without saved photo evidence.

## Portable JSON export

`GET /api/looks/{key}/versions/{version}/export` returns the requested version
from its stored snapshot, including its local look, outfit, and garment keys.
The closed envelope contains `schema_version: 1`, `look`, `garments`, and
`provenance`. `look` contains `key`, `version`, `name`, `appearance`, and either
`outfit: null` or `{key, garment_keys}`. Each garment contains only `key`,
`wording`, and `aside`; the array follows `garment_keys` order and is empty when
there is no outfit. The export is independent of later catalogue changes.

Manually authored local versions export `provenance: null`. A photo-extracted
version exports only `{source: "photo", image_sha256: "..."}`; its full
extraction evidence remains available through the photo-evidence API and is not
included in portable JSON. For imported versions export returns the incoming
annotation retained separately in the private import receipt; the annotation
is not verified evidence. The portable parser
accepts only `null` or the annotation `{source, image_sha256}`, with `source` in
`manual`, `photo`, `assistant`, or `import`; a non-null lowercase SHA-256 value
is allowed only for `photo`. This allowlisted annotation is untrusted data. The
portable content digest covers
the complete canonical envelope, including that annotation. It differs from the
saved version's `content_digest`, which covers only canonical
`{appearance, outfit}` and excludes the name and version number.

The closed envelope includes no photo bytes or paths, session data, or
credentials. Parsing validates the complete shape, orders garments by
`garment_keys`, and rejects duplicate JSON keys and non-JSON numeric constants.

## Portable JSON import

Import is available in the **Looks** view and through the API. It does not
change the legacy `/api/wardrobe/import` behavior.

`POST /api/looks/import/preview` accepts the raw `portable-look-v1` envelope.
Its response includes the import status, original identity, destination or
available choices, exact local garment/outfit mappings, any remaps, and the
`portable_content_digest`, `review_digest`, and `preview_token`. A ready import
uses `choice: "import"`. An occupied source version with different contents,
an unused version older than the latest under that key, or a source identity
already imported with different content requires an explicit choice: `new_version`
uses the latest version plus one under the source key, while `save_copy` uses a
new key at version 1. An unused source key or a free version above its latest
may retain the envelope's declared version. The preview exposes any generated
destination keys and remaps for review. Garment keys containing commas are
remapped because legacy outfits store ordered keys as comma-separated text.
For a conflict when the latest local version is `9223372036854775807`, preview
offers only `save_copy`; no higher SQLite version can be allocated.

Preview and commit requests limit the actual streamed body to 10 MiB, including
when `Content-Length` is missing or inaccurate. Import also limits
`look.version` to SQLite's signed integer range, 1 through
`9223372036854775807`; larger schema-valid values return `422 invalid_look`.

`POST /api/looks/import/commit` accepts a JSON object with exactly these
top-level keys: `envelope`, `preview_token`, `review_digest`, and `choice`. The
`envelope` must be the reviewed portable envelope; `choice` is `import`,
`new_version`, or `save_copy`. The HMAC-signed preview
token binds the canonical content, store state, mappings and available choices,
and expires after 15 minutes. Commit revalidates the reviewed plan and writes
the look version, mapped catalogue entries, and import receipt atomically. If
the store or mapping changed, commit returns a conflict and requires a new
preview.

The receipt records the original pre-remap identity and portable content digest,
the local destination, and exact mappings. An identical re-import is a no-op,
including after remapping, and checks that the recorded destination is intact.
If an envelope already matches a local export, preview reports `already_equal`
and commit is also a no-op. Import `local_origin` is a local classification
separate from portable `provenance`; exports contain local keys and the
allowlisted annotation but never the internal receipt.

## Legacy garment/outfit JSON import

The same preview and commit endpoints also accept the legacy outfit-only shape
when the input has no `schema_version`. The closed object contains one or both
of `garments` and `outfits`; each must be an array. Garments have `key`,
`wording`, and optional `aside`. Outfits have `key`, optional `label`, and
`garments`, which may be an ordered key array or the legacy comma-separated
string. Multiple outfits and garment-only imports are supported. Outfit keys
may reference garments defined in the input or already present in the catalogue;
an unknown reference rejects the whole preview before writes.
Whitespace around keys, wording, aside, labels, and garment references is
stripped. An omitted `aside` becomes an empty string; an omitted or blank
`label` defaults to the outfit key.

For example, preview this raw JSON at `POST /api/looks/import/preview`:

```json
{
  "garments": [
    {"key": "cotton-shirt", "wording": "a cotton shirt"}
  ],
  "outfits": [
    {"key": "summer-layers", "label": "Summer layers", "garments": ["cotton-shirt"]}
  ]
}
```

Preview resolves every reference and returns its exact mappings and any
remapped keys without writing catalogue rows. Commit uses the same request
wrapper as portable import, with the legacy object under `envelope`; choose
`import` when keys are unchanged. If a garment or outfit key conflicts with
different local content, preview generates destination keys and offers only
`save_copy`. Garment keys containing commas are also remapped because the
catalogue stores outfit references as comma-separated text. Commit rechecks the
reviewed catalogue state and, when it writes rows, stores a separate
integrity-verified legacy import receipt with the mapped destination. A receipt
replay checks its destination and is a no-op. An import whose content is
already present is also a no-op.

After an imported receipt exists, a new preview reports `receipt_replay` and
offers only `import`. Retrying the original reviewed commit uses its original
token and choice, including `save_copy` when that was the accepted choice. Use
the choices returned by the current preview; do not infer a choice from the
mapping.

Legacy and portable preview tokens are protocol-specific and cannot be used
across the two import types; both expire after 15 minutes. Both import routes
enforce the same 10 MiB limit against actual streamed request bytes, regardless
of `Content-Length`.

A legacy import writes catalogue garments and outfits only; it does not create
a `saved_look_version`. To explicitly create a named look from an imported
outfit, call `POST /api/looks` with the desired name and its outfit key, for
example `{ "name": "Summer layers", "outfit_key": "summer-layers" }`. This
path leaves the existing `/api/wardrobe/import` behavior unchanged. The Looks
view presents imported outfits for an explicit **Start a look from this outfit**
action; saving that reviewed editor creates the named look. Session authoring
remains a separate operation.

## HTTP API

| Request | Result |
| --- | --- |
| `GET /api/looks` | Latest summary for each look: `[{key, version, name, content_digest}]`. |
| `DELETE /api/looks/{key}` | Archive the look identity; removes it from active listings and preserves exact versions and related history. Returns `404` for an unknown key. |
| `GET /api/looks/{key}/versions/{version}` | Full version: `{key, version, name, content_digest, appearance, outfit}`. |
| `GET /api/looks/{key}/versions/{version}/export` | Closed self-contained `portable-look-v1` envelope for that immutable version. |
| `POST /api/looks/import/preview` | Plan an import from a raw `portable-look-v1` envelope or legacy garment/outfit JSON; does not write catalogue or look rows. |
| `POST /api/looks/import/commit` | Commit the reviewed portable or legacy envelope with its preview token, digest, and explicit choice. |
| `POST /api/looks` | Create version 1 with required `name`, optional `appearance`, and at most one of `garments` or `outfit_key`. |

Each garment definition can provide `key`, `wording`, and `aside`; omit `key`
to create a new garment identity. Omit both outfit fields when creating to save
no outfit; omit them when appending to keep the current outfit, or send
`garments: []` to clear it. A full-version response contains an outfit snapshot
shaped as `{outfit_key, garments: [{key, wording, aside}]}` or `null`. The
snapshot stores complete garment text instead of relying on the current
catalogue. The content digest is derived from canonical `{appearance, outfit}`
content; use `key` and `version` to identify a specific version.

Writes are transactional and use the shared 10 MiB actual-request-body limit,
measured from the streamed request body. Import preview and commit enforce this
limit even when `Content-Length` is missing or inaccurate. When resource
planning is disabled, saved-look writes and both `/api/looks/import/preview` and
`/api/looks/import/commit` return `503`, including for portable and legacy-format
Looks JSON. The gate also applies to direct domain callers. Photo-stage status,
preview, and cancel remain available, as does the existing `/api/wardrobe/import`
behavior. A stale `expected_version` returns `409`; invalid input returns `422`,
and a missing look version returns `404`.
